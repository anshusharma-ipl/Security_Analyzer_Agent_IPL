Agent design

The design decisions behind the agent team: why an agent, who does what, how they are connected, and which agentic patterns are used.

1. Why an agent and not a script

Part of the workDone byReason
Scanning for weak spotsCodeExact and repeatable. No judgement needed.
Tracing whether a finding is reachable from untrusted inputAgentNeeds reading code across files.
Choosing the smallest safe fixAgentThe right answer differs by case. In the golden set case_01, case_05, case_07 and case_11 are all SQL injection with four different right answers.
Deciding when to stop and hand overAgent, with code rulesSafety depends on knowing what it cannot do.

2. The team

Three agents, each with one job and its own tools, and a plain-code orchestrator that is not a model.

RoleDecidesToolsNever
AuditorWhich rule matches are reportable, and their orderlist_files, read_file, run_security_rulesWrites anything
InvestigatorWhether the cause can be traced, and which fix approach suits it, or hand overread_file, read_code_structureWrites anything
Fixer and ValidatorThe patch, and whether to keep, retry once or rejectapply_patch (temporary copy only), run_tests, request_recheckSets the final status
Orchestrator (plain code)Order, limits, approvals, status, reportIts own stepsIs a model

Agents never call each other. Each agent uses only its own tools. The shared state has one owner per field.

3. The architecture

Every handoff goes through the orchestrator. The agents never call each other, and the original files are read only.

4. Agentic patterns used

PatternUsedHow
Multi-agent with an orchestratorYesThree agents with separate jobs, coordinated by plain code.
PipelineYesA scan is seven fixed steps, in a fixed order.
Tool use with least privilegeYesSeven tools. Each agent gets only its own, through its own MCP profile.
Routing and hand-overYesEach finding is routed: fix, retry, or hand to a person.
Reflection and retryYesThe rules run again on the fixed copy, and a failed fix gets one retry.
Human in the loopYesA person approves, edits or rejects every fix.
Parallel agentsNoOne handoff at a time, so every step is logged in order.
Free-form planningNoThe order is fixed by the orchestrator, not chosen by a model.
Retraining the modelNoThe model is not retrained. Failed and rejected fixes are added to the test set instead.

5. State and contracts

PartHow it works
Shared stateOne document owned by the orchestrator. Each field has one writer, so an agent cannot overwrite what it does not own.
ContractsEvery agent reply is checked against a JSON schema before the orchestrator accepts it.
DecisionsThe orchestrator, not an agent, sets the final status. "Verified" comes from test and re-check results.
