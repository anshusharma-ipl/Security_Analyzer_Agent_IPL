How the Security Analyzer works

It scans a Python project for weak spots, proposes a fix for each, tests the fix in a temporary copy, then waits for you to approve, edit or reject it. It never changes your files.

What it does

Finds

SQL injection, command injection and path traversal. It also reports hard-coded secrets, weak password hashes and unpinned packages, but never fixes those.

Proposes and tests

Each fix is applied to a temporary copy, the project's own tests run, and the rules run again. A fix counts as verified only if both pass.

Asks you

Every fix waits for a person. Approved fixes are written to fixes.patch. You apply them yourself.

How it works

A scan is seven fixed steps, run by the orchestrator:

  1. Check the rules file.
  2. Fingerprint your files and make a temporary copy.
  3. The Auditor scans the whole project and ranks the findings.
  4. For each finding, the Investigator traces the cause and the Fixer and Validator writes and tests a patch.
  5. You decide on each fix.
  6. The orchestrator checks that your original files are unchanged.
  7. It writes the log and the report.

Three rules hold the design together. Each agent can use only its own tools. A fix is called verified by the orchestrator from test results, never by the agent's opinion. Anything the agent is unsure about goes to a person.

The canvas is the original design: users, tools, guardrails, quality bar and kill criteria. The roster document explains why there are three agents and one plain-code orchestrator, and records the decision to keep the Auditor as an agent.

How it was built

The project was built with Claude Code, one prompt at a time, following a fifteen-prompt Build Playbook. Each prompt produced code, tests and a commit, and ended with a check you run before moving on.

  1. Foundations. Project setup, the written spec, and the agent roster.
  2. Contracts and tools. JSON schemas for the shared state, seven tools, and an MCP server that gives each agent only its own tools.
  3. Agents and workflow. The shared state, the orchestrator, and three agents. No model endpoint is approved yet, so the agents are deterministic stand-ins that follow the same contracts.
  4. Guardrails. Containment (originals, secrets, hostile text in code, forbidden commands) and decision rules (evidence, "verified", limits, hand-over).
  5. Measurement. A scoring harness against 21 test cases, a red team of ten attacks, and a cost model.
  6. Pilot gate. Eight kill-switch checks and the pilot plan.

The console you are using, and the optional model connection, were added afterwards. See each prompt and what it produced.

Run a live scan, step by step

A live scan needs the console running on your own machine (or a server). The published site on GitHub Pages is read-only: it shows a recorded run and cannot scan anything or call a model.

  1. Start the console. pip install jsonschema, then python ui/server.py, then open http://127.0.0.1:8765.
  2. Give it your code. In New scan, drop your project folder (or a .zip) onto the box, or click it to choose a .zip. The project should include its tests. A rules file is optional; without one the approved default rules are used. For a demo, use demo/shop_demo.zip (one example of each golden case, with a table of expected results).
  3. Connect a model (optional). In Agents enter the endpoint, model name and API key, press Connect then Test, tick which agents should use the model, and tick the box confirming masked code is sent to it. Skip this to use the offline stand-ins.
  4. Press Run scan. The pipeline strip shows the seven steps. When it reaches the review desk, approve, edit or reject each proposed fix, then submit.
  5. Download the result. The report (HTML, Markdown and JSON), the decision log and fixes.patch are on the run's page. Nothing is applied to your original files; a person applies fixes.patch.

From a terminal instead: python -m orchestrator.cli run <your-project-folder> golden/rules.json. With a model, set AI_MODEL_ENDPOINT, AI_MODEL_NAME and ANTHROPIC_API_KEY first and use the console's Agents panel to switch the agents on.

Other commands

You need Python 3.11 or newer and one package: pip install jsonschema.

python ui/server.py              # then open http://127.0.0.1:8765
python -m unittest discover -s tests
python evals/run_evals.py        # score the 21 cases against the quality bar
python kill_checks.py --run      # the eight kill-switch checks

The same scan from a terminal: python -m orchestrator.cli run <folder> golden/rules.json, then finish after a person edits review_queue.json.

Safety. To check a fix, the project's own tests run on the machine that hosts the console. Host it only where that is acceptable, scan only code you trust, and put it behind a token if anyone else can reach it. Hosting notes.

Connect a model

By default the agents are offline stand-ins. To use a real model:

  1. Open Agents in the console and choose Connect a model. Enter the endpoint, model name and API key. Or put AI_MODEL_ENDPOINT, AI_MODEL_NAME and ANTHROPIC_API_KEY in a .env file and press Use .env.
  2. Press Test. It sends one tiny message with no project data.
  3. Tick the agents that should use the model and confirm that masked code is sent to the endpoint.
  4. Run a scan. The trace shows how many calls and tokens each handoff used.

The harness fills in the paths, rules file and test command itself. Secrets and personal data are masked before anything is sent. The Auditor can keep only findings the rules tool returned. The Fixer's test and re-check results come from the tools, not from the model. A patch that edits tests, requirements or the rules file is refused. The key is held in memory and never written to disk.

Not yet proven. This layer is tested against a mock server that speaks the Anthropic Messages format. It has not been run against a live model. Only that format is supported; another provider needs an adapter in agents/model_agents.py.
