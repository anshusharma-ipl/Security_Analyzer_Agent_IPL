Guardrails

What can go wrong, and the guardrails that stop it.

In plain words

An AI tool can invent things, obey instructions hidden in code, or break working code. Each risk below has a guard. The checks that stop a run at once are on the Kill criteria and rollback page.

What can go wrong, and what stops it

What can go wrongWhat stops itStopped when tested?
A fix is marked verified but is wrongOnly the orchestrator can mark a fix verified, and only after passing tests and a clear re-checkNo (red-team case 14)
A fix breaks working codeTests must pass first, and a person reviews every fixNo (red-team case 14)
Secrets reach the AI providerThey are replaced by placeholders before any model callYes
Hidden instructions in code steer the modelCode is read as text and never obeyed, and the attempt is loggedYes
A fix runs something harmfulForbidden commands are refused, only the temporary copy is written, and a fix may never change the project's testsYes
The model reports a problem that is not realA finding with no file, line and code is droppedYes
The rules file is wrongIt is checked against a schema at the start of every runYes
An agent sends bad numbers to get around the run limitsA handoff with missing or negative usage numbers is rejected, and the finding goes to a personYes
Your original files changeThey are fingerprinted before and after, and any change stops the runYes
A fix is applied without a person's approvalEvery fix waits in a review queue with its evidence, diff and test results. A person approves, edits or rejects it, and applies the approved fixes (fixes.patch) themselves.Yes
The AI provider updates the model and it starts giving different answersEvery run records the model version, so a change can be traced. After a change, the test cases are run again and compared with the earlier results.By hand (a person has to start the test run)

Stopped when tested? Yes: the tests pass and no attack gets through. No: a red-team attack beat this guardrail, so open the case to see how. By hand: a person has to start the check. Nothing runs it automatically.

The checks come in three kinds. Code tests check that the guardrails work: tests/test_decisions.py and tests/test_containment.py cover the ones above. kill_checks.py checks the eight kill criteria. evals/run_evals.py checks how the agents behave on the test cases.

Red team: 7 of 10 attacks held. Three remain (cases 14, 15 and 19), each with its smallest proposed fix on the Evals and testing page.
