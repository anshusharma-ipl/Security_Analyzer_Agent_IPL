Problem and idea

Security scanners list problems but leave the fixing to people. This agent team finds the weak spots, prepares a tested fix for each one, and lets a person decide.

View the project canvasThe one-page design this project started from.

The problem

Security scanners produce long lists of problems. Turning each problem into a safe, tested fix is still manual work.

PainWhy it hurts
Long, noisy listsMany findings are false alarms or low risk. Engineers spend their time working out which are real before they fix anything.
Context is scatteredTo understand one finding, an engineer reads several files, the scan report and tickets.
Weak testsPassing tests do not prove the weakness is gone, or that the code still behaves the same.
Repeated explanationsThe same investigation is written up twice, once for the security engineer and once for the code reviewer.

These pain points come from the scenario in the Canvas (a fictional company). They are hypotheses to validate in the pilot, not measurements.

Why trust in scanners falls. A scanner reports a problem but does not prove it is real, explain it or fix it. When many reports turn out to be noise, engineers stop trusting the list and ignore it, so real problems are missed.

What we are building

The Security Analyzer is a team of three AI agents: the Auditor, the Investigator, and the Fixer and Validator. You give it a Python project, its tests and an approved rules file. It finds and ranks the weak spots, then prepares and tests a fix for each one in a temporary copy. A person approves, edits or rejects every fix. It never changes your original files, and it never commits or deploys.

Who it is for

WhoNeed
Software engineers who fix security findings alongside their feature work (the canvas persona is Meera)Faster investigation and checking, with enough evidence to approve a fix with confidence. Not another list of possible problems.
The security engineer who owns the rules fileFindings that follow the approved rules, and a record of every decision.

The pilot has three to five engineers on one non-production repository.

Non-goals

Not in scopeMeaning
AI-based detection rulesFindings come only from the approved rules file.
Automatic apply, commit, pull request, deploy or dependency changeA person always applies a fix.

The job and what success looks like

The jobWhen a project has security findings, see only proven ones, each with a tested fix. The safe fixes are approved quickly, and the time goes to the ones that need a person.
Success in the pilotAt least 30% less human time per scan (to be measured), no unsafe action, and a false-fix rate at or below 5%.
