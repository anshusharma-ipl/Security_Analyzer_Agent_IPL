Summary

It scans a Python project for weak spots, proposes a fix for each, tests the fix in a temporary copy, then waits for you to approve, edit or reject it. It never changes your files.

Finds

SQL injection, command injection and path traversal. It also reports hard-coded secrets, weak password hashes and unpinned packages, but never fixes those.

Proposes and tests

Each fix is applied to a temporary copy, the project's own tests run, and the rules run again. A fix counts as verified only if both pass.

Asks you

Every fix waits for a person. Approved fixes are written to fixes.patch. You apply them yourself.

Proof at a glance

9 of 11golden cases pass
2 of 10red-team attacks held (8 weaknesses found)
7 of 10findings fixed in a live GPT-5 run
about $0.75per scan of the demo project

Golden cases are realistic projects with a known answer. The red team is a set of attacks written to break the system, so finding weaknesses is its job. The live run is one real scan, not a benchmark. Details are on the Results page.

The problem and the idea

The problem

Application-security scanners produce long lists of findings. Turning a finding into a safe, tested fix is still manual work.

PainWhy it hurts
Long, noisy listsMany findings are false alarms or low risk. Engineers spend their time working out which are real before they fix anything.
Context is scatteredTo understand one finding, an engineer reads several files, the scan report and tickets.
Weak testsA passing test run does not prove the weakness is gone or that behaviour is unchanged.
Repeated explanationsThe same investigation is written up again for the security engineer and the code reviewer.

Why trust in scanners falls. A scanner reports a problem but does not prove it is real, does not explain it and does not fix it. When many reports turn out to be noise, engineers stop believing the list and start ignoring it, so real issues are missed.

What we are building

An agent team that takes a Python project, its tests and an approved rules file. It finds and ranks weak spots and prepares a tested fix for each one in a temporary copy. It hands every fix to a person, who approves, edits or rejects it. It never changes the original files and never commits or deploys.

Who it is for

WhoNeed
Software engineers who resolve security findings and write the fixes alongside feature work (the canvas persona is Meera)Faster investigation and verification, with the evidence needed to approve a fix confidently. Not another list of possible problems.
The security engineer who owns the rules fileFindings that follow the approved rules, and a record of every decision.

The pilot has three to five engineers on one non-production repository.

Non-goals

Not in scopeMeaning
AI-based detection rulesFindings come only from the approved rules file.
Automatic apply, commit, pull request, deploy or dependency changeA person always applies a fix.

The job and what success looks like

The jobWhen a project has security findings, see only proven findings, each with a tested fix, so the safe ones are approved quickly and the time goes to the ones that need a person.
Success in the pilotAt least 30% less human time per scan (to be measured), no unsafe action, and a false-fix rate at or below 5%.
