3. Comparing manual and agent-assisted time on the same labelled examples

The examples. The security engineer labels each one before any run: it is a true or false positive, its rule, file and line, the right fix approach, and whether it should go to a person. Start from golden/ (21 cases: the 11 canvas types plus 10 red-team cases) and add the real findings of the pilot repository, up to about 20 labelled examples for the first comparison (AGENTS.md section 7). Labels are written to an expected.json in the same format and are never changed after a run.

The two ways. Every example is worked twice, by two different engineers, so nobody sees the same example in both modes:

ModeWhat the engineer doesClock startsClock stops
ManualTriage, reproduce, find the cause, write the fix, re-test, document, and have it reviewed, in a scratch copy of the repository (no commit)The finding is handed overA tested fix and a written note are ready for review
Agent-assistedReads the handoff package in review_queue.json (evidence, cause, diff, tests, re-check, residual risk), then approves, edits or rejects; reworks the fix by hand if rejectedThe review queue opensThe decision is recorded and, if rejected, a tested manual fix is ready

The agent's own run time is recorded separately (state.counters.elapsed_seconds) and is not engineer time.

Counterbalancing. Assign examples to engineers so each engineer does half the examples manually and half agent-assisted, alternating which mode comes first, and so no two examples of the same class always go to the same mode. The security engineer scores every result against the label without knowing which mode produced it.

What is recorded for every example (one row in a time log, TO FILL: where it lives): example id, rule, mode, engineer, minutes by stage (triage, reproduce, fix, re-test, document, review), tests pass after, re-check clear, correct against the label (yes, partly, no), rework needed (minutes), outcome (approved, edited, rejected, handed to a person), reviewer comment.

How it is reported. Median and range per mode and per class; the share of agent-assisted examples that ended approved, edited, rejected or handed over; false-fix count. With about 20 examples these are directional. No "% of time saved" is claimed until it is measured here (AGENTS.md section 7), and the figure is shown only with the number of examples behind it.

Not in evals/ yet. evals/run_evals.py computes the quality metrics on the golden set with a simulated reviewer. The time log, the scoring of human-completed examples and the manual-versus-assisted summary are not built; the pilot starts them.

4. Human review SLA (confirmed)

Canvas section 12 says only "Define during pilot; until reviewed, the proposal remains unapplied". The value below is the team decision recorded in AGENTS.md section 5, confirmed as the pilot SLA.

  • A person reviews a proposal within 1 business day.
  • After 1 business day it is flagged overdue at the top of the review list.
  • After 5 business days, or if the code changed, it is marked expired, unapplied and re-run.
  • The MVP sends no reminder and does no escalation; reminders may be added in the pilot.
  • Nothing is ever applied automatically, at any age.

Status in code: not implemented. The review queue (review_queue.json) has no timestamp check, overdue flag or expiry. For the pilot, either build it or track review age by hand in the time log. TO FILL: which.

5. Immediate kill criteria (canvas section 16)

Each is checked automatically after every agent handoff and again before the report is written (kill_checks.py, called from orchestrator/workflow.py). A check that fires stops the run, writes alert_kill_<criterion> to the decision log and alert.json to the run folder, and writes no report. Each has a test that triggers it on purpose (tests/test_kill_checks.py); show the table with python kill_checks.py --run.

Contacts an unauthorized network endpointcheck_network_not_approved: a guard refuses any connect or DNS lookup except loopback and the approved model endpoint (AI_MODEL_ENDPOINT in .env, none today)test_kill_network_not_approved
Exposes an unmasked secretcheck_unmasked_secret: every agent output and the decision log scanned for secrets, emails and phone numberstest_kill_unmasked_secret
Applies a fix without approvalcheck_fix_without_approval: every patch written for a person traces to an approved or edited decision with a named reviewer; fixes.patch must not exist without onetest_kill_fix_without_approval
Fails to create a complete audit logcheck_audit_incomplete: no gap in the log sequence, handoffs, statuses or approvals; the decision log must be written and read back wholetest_kill_audit_incomplete
Installs or removes a packagecheck_package_changed: the interpreter's installed package set compared before and after; an install command attempttest_kill_package_changed
Performs a commit, push, merge or deploymentcheck_vcs_or_deploy: git HEAD, every ref, packed refs and merge state compared before and after; a git or deploy command attempttest_kill_vcs_or_deploy

Limits, stated plainly. The network guard and the package check cover this Python process (the orchestrator and the agents), not the child process that runs the project's tests. The container planned for the pilot (AGENTS.md section 8) is the hard wall for what a child process can do. The secret check can only find what the masker recognises: the red-team case case_21_secrets_masking_gaps shows secret shapes it does not, which is a separate open finding.

7. Before the pilot can start

This is where the work stands today, not a plan.

  1. No model is connected. No endpoint is approved; the three agents are offline stand-ins. The pilot needs the platform or security owner to approve an endpoint (AGENTS.md open question 1) and model-backed agents.
  2. The quality gates do not pass yet. On the golden set (directional): verified-fix success 50% against 75%, false-fix rate 25% against 5%.
  3. Eight of ten red-team attacks currently break the system (python evals/redteam.py), with the smallest fix proposed for each and none applied. Those that touch a kill criterion (an agent can edit the project's own tests, secret shapes the masker misses) should be fixed or explicitly accepted before real code is used.
  4. Open inputs: participants (section 2), the review SLA (section 4), the time-log location (section 3), model prices and the engineer rate (docs/pricing.json).

8. Scale-up criteria (canvas section 16)

Expand only when all safety gates remain satisfied; benchmark thresholds are met; human reviewers accept at least 70% of verified proposals; no regression is attributed to an approved agent proposal during the pilot; a second team can adopt and maintain the same rule format; costs remain below the measured manual-review cost; and code-processing and model-provider policies are approved.

Biggest assumption to test first (canvas section 16): existing project tests, combined with an independent security re-check and human review, are strong enough for engineers to trust the proposed fixes.
