1. Summary

The problem

Application-security scanners produce long lists of findings. Turning a finding into a safe, tested fix is still manual work.

PainWhy it hurts
Long, noisy listsMany findings are false alarms or low risk. Engineers spend their time working out which are real before they fix anything.
Context is scatteredTo understand one finding, an engineer reads several files, the scan report and tickets.
Weak testsA passing test run does not prove the weakness is gone or that behaviour is unchanged.
Repeated explanationsThe same investigation is written up again for the security engineer and the code reviewer.

Why trust in scanners falls. A scanner reports a problem but does not prove it is real, does not explain it and does not fix it. When many reports turn out to be noise, engineers stop believing the list and start ignoring it, so real issues are missed.

What we are building

An agent team that takes a Python project, its tests and an approved rules file. It finds and ranks weak spots and prepares a tested fix for each one in a temporary copy. It hands every fix to a person, who approves, edits or rejects it. It never changes the original files and never commits or deploys.

Who it is for

WhoNeed
Software engineers who resolve security findings and write the fixes alongside feature work (the canvas persona is Meera)Faster investigation and verification, with the evidence needed to approve a fix confidently. Not another list of possible problems.
The security engineer who owns the rules fileFindings that follow the approved rules, and a record of every decision.

The pilot has three to five engineers on one non-production repository.

Why an agent and not a script

Part of the workDone byReason
Scanning for weak spotsCodeExact and repeatable. No judgement needed.
Tracing whether a finding is reachable from untrusted inputAgentNeeds reading code across files.
Choosing the smallest safe fixAgentThe right answer differs by case. In the golden set case_01, case_05, case_07 and case_11 are all SQL injection with four different right answers.
Deciding when to stop and hand overAgent, with code rulesSafety depends on knowing what it cannot do.

Non-goals

Not in scopeMeaning
AI-based detection rulesFindings come only from the approved rules file.
Automatic apply, commit, pull request, deploy or dependency changeA person always applies a fix.

2. User job and success

The jobWhen a project has security findings, see only proven findings, each with a tested fix, so the safe ones are approved quickly and the time goes to the ones that need a person.
Success in the pilotAt least 30% less human time per scan (to be measured), no unsafe action, and a false-fix rate at or below 5%.

3. How it behaves

3.1 Inputs

InputRule
Source folderOne Python project, read only. At most 200 files are scanned.
Rules filerules.json, checked against schemas/rules.schema.json before anything runs. One security engineer owns it. The agent never edits it.
TestsThe project's own test command (default python -m unittest discover -s tests), run in the temporary copy. Each test run is stopped after 120 seconds; a run that times out cannot verify a fix.
LimitsThe run limits in 3.2.

3.2 Limits and default values

If a limit is reached, the run stops cleanly: findings not yet handled are marked "not processed" and the review queue is still written.

LimitDefaultWhat it does
File cap200 filesLists no more than this many files; the rest are not scanned and the report says so.
Step cap50 stepsOne step is one handoff to an agent. Stops runaway loops.
AI-call cap60 callsCounts every model request. The console raises it to 150 for runs with a model.
Token cap400,000 in and 60,000 outStops spending on a single scan.
Time cap20 minutesStops a scan that takes too long. The console raises it to 40 minutes for runs with a model.
Test time limit120 seconds per test runStops a hanging test suite.
Retries per fix1If a fix fails its tests or re-check, one more attempt is allowed, then it goes to a person.
Confidence gate0.70A finding reported by the AI model with less than 70% confidence goes to a person. Findings from the rules are not affected.

3.3 Outputs

Every run writes these files.

FileWhat it holds
report.md / report.htmlThe readable report: each finding, its evidence, the fix and the result. report.html is the version shown in the console.
report.jsonThe same report as data, for other tools.
review_queue.jsonThe fixes waiting for a person to approve, edit or reject.
decision_log.jsonEvery decision with its time and who made it (an agent, the orchestrator or a person).
state.jsonThe final shared state of the run, including counters for steps, AI calls and tokens.
fixes.patchThe approved fixes as one patch, only if something was approved. A person applies it.

3.4 What each finding carries

Every finding in the report has the same fields, so a reviewer can decide without searching.

FieldWhat it shows
Rule, file, lineWhat was found and where.
Quoted codeThe exact line, as proof. A finding without proof is dropped.
Severity and confidenceHow serious it is and how sure the Auditor is.
Traced causeWhere the untrusted input comes from, or why that could not be traced.
DiffThe proposed change.
Tests before and afterWhether the project's tests passed before the change and after it.
Re-checkWhether the rules, run again on the fixed copy, still find the problem.
Residual riskWhat the fix does not cover.

Every agent reply is checked against a JSON schema before the orchestrator accepts it.

3.5 Roles and tools

RoleDecidesToolsNever
AuditorWhich rule matches are reportable, and their orderlist_files, read_file, run_security_rulesWrites anything
InvestigatorWhether the cause can be traced, and which fix approach suits it, or hand overread_file, read_code_structureWrites anything
Fixer and ValidatorThe patch, and whether to keep, retry once or rejectapply_patch (temporary copy only), run_tests, request_recheckSets the final status
Orchestrator (plain code)Order, limits, approvals, status, reportIts own stepsIs a model

Agents never call each other. Each agent uses only its own tools. The shared state has one owner per field.

3.6 When the agent hands over to a person

A person approves every fix. In addition, the agent stops and hands a finding over in the situations below.

SituationWhat happens
It cannot trace the causeEngine and evals: handed to a person. Console: see "Unclear cause" below.
No tests existHanded over. Without tests a fix cannot be verified.
The fix needs a redesign or a dependency changeHanded over.
Retries are used up, a limit is hit, or anything looks unsafeHanded over.
The finding is a secret, a weak hash or an unpinned dependencyReported only. Never patched. See "Report-only findings" below.

Unclear cause (console only). A *caller* is the code that calls the vulnerable function. If no caller is visible in the project, the agent cannot tell whether untrusted input reaches that function. The fix itself, for example replacing a string-built SQL query with a ? placeholder, is safe either way. So the console still prepares that small local fix and marks it "cause not traced: check where this function's input comes from". The tests and re-check still have to pass, and a person decides. If the fix would need a redesign, it still goes to a person. The engine and the evals keep the stricter rule and hand these findings over.

Report-only findings. The agent never patches these three, because a code change cannot fix them:

FindingWhy no patchTask shown to the person
Hard-coded secretThe secret is already exposed. The key must be replaced.Rotate the key and move it out of the code.
Weak password hashChanging the algorithm breaks stored passwords.Choose a password hash and plan the migration.
Dependency pinA new version needs a compatibility check.Raise the pin and run the tests.

A patch causes a regressionMedium, highSmallest change, tests green first, human review, nothing applied automaticallytests/test_decisions.py
Secrets or personal data reach the model vendorMedium, highMasking before any model call; a leak scan on the log and reporttests/test_containment.py; red-team case 21 (masking gaps remain)

Red team: 8 of 10 attacks still break the system. They are listed on the Test cases page with the smallest proposed fix for each. None is fixed yet.

4.2 Guardrails by stage

StageGuardrails
InputThe rules file is checked and the file count is capped before anything runs. Only the given folder is read; links that leave it are refused. Secrets, email addresses and phone numbers become placeholders before text reaches a model. Hostile text in code is treated as data and logged as prompt_injection_attempt. Test commands that install packages, commit, push or deploy are refused.
OutputEvery agent reply must pass its JSON schema. A finding without proof is dropped and logged. A patch must apply and still parse. "Verified" is set only by the orchestrator. The log and report are scanned for unmasked sensitive values. The originals are fingerprinted again at the end; any change stops the run. The model-backed Fixer refuses patches that touch tests, requirements, the rules file or paths outside the copy; the orchestrator does not yet enforce this for every agent (red-team case 20).
Human reviewEach proposed fix sits in a review queue with its evidence, diff, test results and residual risk. A person approves, edits or rejects it; rejecting and editing need a reason. An edited patch goes through the same tests and re-check. Approved fixes become fixes.patch, which a person applies.

6. How we measure

We score the agents against a set of small projects with known right answers, then repeat the scoring whenever something changes.

6.1 What we score against

ItemDetail
Golden dataset21 cases. 11 are the canvas types. 10 are red-team attacks. Each has an answer key (expected.json). The set grows from failed and rejected fixes.
Red-team attacksInstructions hidden in code, weak tests, a re-check that blocks a pair, broken replies, unparsable patches, safe-looking code, forbidden writes, secrets the masking misses.

6.2 How each result is judged

MethodUsed forHow
Checks in codeVulnerability present, test outcome, source unchanged, files inside the workspace, valid syntax, patch size, evidence and audit completenessExact. Pass or fail.
A second model as judgeWhether the cause explanation is right, whether the patch is the smallest maintainable one, whether the residual-risk note is accurateAnswers yes, no or unsure from masked text. Never changes a status. Built and tested with a stub; no judge model is set up yet, so there is no live result. Before relying on it, compare it with a person on at least 20 findings.

9. Kill criteria and rollback

Kill criteria: stop at once if the agent

  • modifies an original file;
  • writes outside the temporary copy;
  • contacts an endpoint that is not approved;
  • exposes an unmasked secret;
  • applies a fix without approval;
  • fails to write a complete audit log;
  • installs or removes a package;
  • commits, pushes, merges or deploys.

Each of the eight has an automatic check and a test (kill_checks.py).

Rollback: go back to the previous rules, prompts, model or scan-only mode if

Trigger
High-severity recall falls below the threshold
The false-fix rate goes above 5%
Reviewers reject more than half of the verified proposals across two evaluation cycles
Model or execution cost goes above the cost of fixing by hand
The benchmark drops after a model or prompt change

Rollback and scale-up details are in docs/PILOT.md.
